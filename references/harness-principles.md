# Harness Engineering 理念速查卡

> 供 AI 在执行诊断问答时随时查阅的浓缩知识库。
> 内容蒸馏自真实工程实践，通用于任意 AI Skill 改造场景。

---

## 一、核心公式

```
AI 输出质量 = AI 能力 × 上下文质量
```

**乘法的含义**：上下文质量趋近于零时，AI 再强也没用。
**杠杆点**：提升上下文质量比提升模型能力更高效，因为上下文质量完全掌握在团队手中，而模型能力依赖外部。

---

## 二、五类上下文缺口

| 缺口类型 | 典型症状 | AI 的「盲区」 |
|---------|---------|-------------|
| **隐性规范** | AI 不知道某些约束存在 | 团队约定的参数格式、命名规则、边界条件 |
| **历史决策** | AI 重复走已被否定的路 | 「为什么当时选了 A 不选 B」 |
| **能力边界** | AI 猜 API 参数、猜数据格式 | 某个方法/服务的真实限制 |
| **跨会话经验** | 同一个错误反复出现 | 上次踩的坑，新会话完全不知道 |
| **演进轨迹** | AI 不知道某个模块历史上踩过什么大坑 | 过去的重大问题和处理方式 |

## 三、三层知识架构

```
team/        最稳定层，跨场景通用
             全局规范、必须遵守的底线、跨项目共用的约定

framework/   框架层，中频更新，跨任务通用
             执行规范、API 速查、质量护栏、流程模板

project/     项目层，高频演进，场景特有
             特定约束、踩坑经验、历史决策、外部依赖行为
```

**加载原则**：每个执行阶段只加载当前阶段需要的层，建立 INDEX.md 路由表。

## 四、门禁设计矩阵

```
              修改代价
        低 ◄──────────────────► 高
        │ 编辑文字 │ 重新执行 │ 用户反馈后重做
        └─────────┴──────────┘
        ▲ 在这里设门禁，代价最低 ▲
```

**好门禁的三个特征**：
1. **结构化输出**：JSON 文件，不是控制台打印（可追溯）
2. **程序派生 passed**：Python/JS 布尔值，不是 AI 判断
3. **WHITELIST 是代码**：豁免枚举附文字证据，不是 AI 口头声明

## 五、Self-Refinement 闭环

```
出错/被修正 → AI 判断：一次性问题 or 模式性问题？
                              │ 模式性
                              ▼
                     提议沉淀到哪一层
                     team/ or framework/ or project/
                              │ 用户确认
                              ▼
                     生成 experience 文档
                     ## Experience NNN: {title}
                     Date / Problem / Root Cause / Fix / Rule
                              │
                              ▼
                     下次执行前，AI 在对应阶段读取 experiences/
                     → 同类问题不再重犯
```

## 六、prompt 是软的 vs 机制是硬的

| 软约束（靠 prompt） | 硬约束（靠机制） | 替换方向 |
|-------------------|----------------|---------|
| 「请遵守格式规范」 | 运行检查脚本，读结构化结果 | 写 gate_check 脚本 |
| 「完成后告诉我结果」 | 读 gate_result.json，passed:true 才能继续 | 状态文件驱动 |
| 「不要使用 X 方法」 | WHITELIST 枚举，代码层面阻断 | 硬编码白名单 |
| 「注意参数格式」 | char_budget/格式规范在 YAML 矩阵里，脚本自动检查 | 能力矩阵 + 门禁脚本 |

## 七、反模式速查（来自真实工程实践）

### 反模式 A：完成声明先于完成证书
AI 在没有运行任何验证代码的情况下，说「任务完成」。
**解法**：SKILL.md 顶部写明——「在 gate_result.json passed:true 之前，禁止说出完成类措辞」

### 反模式 B：Evaluator 用软话糊过评审（来自 UI Harness v2 实战）
「基本一致」「可接受范围」「engine 内部行为」——字面没错，但把需要标记的问题挤出去了。
**解法**：逐项 checklist，每格只能填 ok / fail(reason)，没有灰色地带

### 反模式 C：全量加载 = 信息噪音
所有知识全部注入上下文，AI 做简单任务时也读所有复杂规范。
**解法**：三层知识分离，INDEX.md 路由表，每阶段只读需要的

### 反模式 D：经验修完即丢
每次出错修复后，下次同样会再犯，因为经验只活在当前对话里。
**解法**：experiences/ 目录 + Self-Refinement 协议，模式性修正必须持久化

### 反模式 E：角色越权（来自 UI Harness v2 实战）
负责「判断下一步」的角色同时也有执行权，于是绕过了自己的判断。
**解法**：「判断者」不持有执行工具，「决策」和「执行」session 隔离

## 八、战略十问核心判断维度（用于 R6 校准）

| 问题 | 用途 |
|------|------|
| 赢的判断：改造后成功标准是什么？ | 防止改造方向偏离真实需求 |
| 真实市场：使用频率如何？ | 决定改造投入是否值得 |
| 可持续能力：哪些是一次投入持续生效的？ | 优先做复利型改造 |
| 关键约束：有哪些不能动的？ | 避免改造后兼容性问题 |
| 速度 vs 质量：用户更在意哪个？ | 决定 Fast Track 条件设计 |
| 机制 vs 信念：靠 prompt 要求 AI 自觉是信念，靠脚本强制是机制 | 硬约束替代软约束 |

## 九、七步成诗 × Harness 诊断映射

| 七步成诗 | Harness 诊断对应 |
|---------|----------------|
| 第1步：界定问题 | R1 产品定位 + R7 问题陈述确认 |
| 第2步：分解问题 | R2 上下文 + R3 流程 + R4 门禁 + R5 经验（四维分解）|
| 第3步：优先排序 | R6 战略十问校准（P0/P1/P2/P3 优先级）|
| 第4步：分析 | 每轮的「诊断框架」方块 |
| 第5步：综合 | R7 四维缺口评级汇总 |
| 第6步：交流 | 改造方案 Action Plan 输出 |
| 第7步（隐含）：实施 | 用户按 Action Plan 执行，验证 Checklist |
