# Harness Skill Upgrader

**把任意 AI Skill 从「感觉驱动」升级为「工程约束驱动」的顾问 Skill**

## 这是什么？

一个用来改造其他 Skill 的 Skill。

当你的 AI Skill 出现以下问题时，它就是你需要的：

- 「每次运行结果都不一样，不稳定」
- 「AI 总是犯同样的错，修了下次还犯」
- 「说是完成了，但其实什么都没检查」
- 「Skill 越写越长，AI 越读越乱」
- 「想工程化，但不知道从哪里下手」

通过 **5-7 轮结构化诊断问答**（底层融合七步成诗 × 战略十问），精准找到你的 Skill 的核心缺口，输出可直接执行的 Harness 改造方案。

## 核心理念

### AI 输出质量 = AI 能力 × 上下文质量

这是乘法，不是加法。

大多数 Skill 的问题不在 AI 能力不够，而在**上下文质量太低**。上下文质量趋近于零时，再强的模型输出也是零。而上下文质量完全掌握在你手中——这就是杠杆点。

### Vibe Coding 的三个结构性缺陷

```
信息损耗 ── 同一个 Skill 每次运行结果不同
            需求/约束从没有显式化成工程制品

知识孤岛 ── AI 不知道历史决策、领域规范、踩坑经验
            知识散落在聊天记录里，无法跨会话复用

验证断档 ── 「能跑」就算完成，错误悄悄积累
            门禁是 AI 口头判断，不是机读规则
```

### Harness Engineering 四大组件

```
上下文工程    知识分层 · 渐进披露 · 按需加载
运行时控制    多阶段流程 · 状态持久化 · 断点恢复
门禁机制      机读化检查 · 结构化 checklist · 程序派生 passed
生命周期管理  经验沉淀 · Self-Refinement 闭环 · 知识资产化
```

### 两条铁律

**铁律一：LLM 把生成「完成声明」误当作完成了**

> AI 说「任务完成」的那一刻，对它来说任务就已经结束了。
> 不管实际上有没有运行任何检查代码。

解法：门禁必须是程序运行的结果（结构化 JSON 文件）。`passed` 是 Python 布尔值，不是 AI 的感受。

**铁律二：prompt 是软的，机制是硬的**

> 靠 prompt 要求 AI 自觉遵守规则，就像靠告示牌防止闯红灯。

解法：能用脚本/代码/结构化 JSON 约束的，就不要靠 prompt。反模式要具象化写在 SKILL.md 顶部，不是泛化说「请遵守规则」。

## 诊断框架：7 轮问答

底层融合两套方法论：

- **七步成诗**：界定问题 → 分解问题 → 优先排序 → 分析 → 综合 → 交流 → 实施
- **战略十问**：赢的判断、真实市场、可持续能力、关键约束、速度 vs 质量

每一轮答案决定下一轮问什么，是**对话式深挖**，不是线性填表。

```
R1  产品定位   → 界定：这个 Skill 解决什么问题、服务谁、产出什么
R2  上下文质量 → 分解：全量加载 / 知识孤岛 / 能力边界不清 / 经验未持久化
R3  流程完整性 → 分解：一步直达 / 无确认点 / 错误发现太晚 / 无断点恢复
R4  门禁现状   → 分解：AI 口头 / 无追溯 / 豁免权在 AI 嘴里
R5  经验沉淀   → 分解：修完即丢 / 同类错误反复 / 跨会话知识断裂
R6  战略校准   → 优先：成功标准 / 使用频率 / 改造投入是否值得 / 关键约束
R7  问题陈述   → 综合：四维缺口评级 + 改造优先顺序确认
```

| 维度 | 当前状态 | 缺口 | 优先级 |
|------|---------|------|-------|
| 上下文质量 | … | … | 🔴/🟡/🟢 |
| 流程完整性 | … | … | 🔴/🟡/🟢 |
| 门禁机制 | … | … | 🔴/🟡/🟢 |
| 经验沉淀 | … | … | 🔴/🟡/🟢 |

### 四个优先级层

```
P0  立即改造（10-30 分钟，不写代码）
    → 在 SKILL.md 顶部加「常见崩坏模式」具象化警告

P1  门禁机读化（1-3 小时）
    → 写 gate_check 脚本，输出 gate_result.json
    → passed 由程序派生，不由 AI 口头判断

P2  知识分层（2-4 小时）
    → SKILL.md 从全量加载精简为入口+索引
    → references/ 三层结构 + INDEX.md 路由表

P3  Self-Refinement 闭环（可选）
    → experiences/ 目录 + 协议
    → 模式性错误持久化，跨会话复用
```

### 快速验证 Checklist

```
□ SKILL.md 顶部有「常见崩坏模式」章节？
□ 门禁由脚本执行，产出 JSON 文件（不是控制台打印）？
□ passed 由程序派生，不是 AI 口头判断？
□ experiences/ 在 SKILL.md 对应阶段有读取入口？
□ 上下文按需加载（有 INDEX.md 路由表）？
□ SKILL.md 改造后比改造前更短、更聚焦？
□ 反模式警告已写入 SKILL.md 最顶部？
```

## 使用方法

### 在 WorkBuddy / Codebuddy 中使用

```
你：帮我 Harness 化这个 skill
AI：（自动加载 harness-skill-upgrader，开始 R1 问答）
```

或者直接描述问题：

```
你：我的 skill 总是出同样的错，帮我找找根因
你：这个 skill 每次结果不一样，怎么优化？
你：想让 AI 在这个 skill 里按规矩做事
```

### 手动安装

```bash
# 用户级安装（所有项目可用）
cp -r harness-skill-upgrader ~/.workbuddy/skills/

# 或克隆到 skills 目录
git clone https://github.com/likaku/harness-skill-upgrader \
    ~/.workbuddy/skills/harness-skill-upgrader
```

## 典型案例：一次真实改造

**背景**：一个 AI Skill 的 SKILL.md 有 3,967 行，每次运行全量加载，1 道 QA 门禁，无经验沉淀。

**诊断结论**（经过 7 轮问答）：
- 上下文质量 🔴：全量加载 ~6000 tokens，信息噪音大
- 流程完整性 🟡：有 QA 门禁但无前置阶段，错误在渲染后才发现
- 门禁机制 🔴：门禁结论由 AI 口头判断，无机读追溯
- 经验沉淀 🔴：修完即丢，同类错误下次还会犯

**改造后**：
- SKILL.md 从 3,967 行精简到 245 行（入口+索引）
- 新增 `references/` 三层知识结构，按需加载
- 新增 `gate_check.py` — S4 门禁机读化，`passed` 由程序派生
- 新增 `gate_check_s3.py` — S3 内容门禁，在渲染前拦截 API 格式错误
- 新增 `experiences/` — 4 个分类文件，15 条持久化经验

**A/B 测试结果**（相同提示词）：

| 指标 | 改造前 | 改造后 |
|------|-------|-------|
| 洞见标题比例 | 0/7（全是标签词）| 8/12（完整句子含判断）|
| 版式多样性 | 约 5 种 | 9 种 |
| API 格式错误 | 3 个（执行后才发现）| 0 个（前置门禁拦截）|
| 首轮门禁通过 | 否（需要多轮修复）| 是（gate_check 输出 passed:true）|

## 关于门禁设计的一个反直觉发现

改造前的 QA 分数反而更高（95 vs 92）。

原因：改造后使用了更复杂的版式，触发了更多 QA 规则。**QA 分数衡量的是布局健康度，不是内容质量**——它们是不同维度。

这个发现本身就是 Harness 理念的体现：**量化指标只能测量它能测量的东西**，门禁设计要盯住真正重要的维度，而不是盯住最容易测量的指标。
